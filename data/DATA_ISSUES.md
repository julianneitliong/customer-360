# Known data issues (built in on purpose)

All data is synthetic, generated by `scripts/generate_data.py`. These are the problems the pipeline has to solve.

## CRM export (`raw/crm/`)
| Issue | Where | Handled in |
|---|---|---|
| Account IDs appear as both 15-char and 18-char Salesforce IDs | `contacts.AccountId`, `opportunities.AccountId`, billing `metadata.crm_account_id` | staging: normalize to the first 15 chars |
| 4 duplicate accounts (same company, different ID and name spelling) | `accounts` | intermediate: dedupe on cleaned domain, keep the oldest record |
| Segment values inconsistent (`SMB`, `smb`, `Small Business`, `MM`, `ENT`, trailing spaces) | `accounts.Customer_Segment__c` | staging: map to SMB / Mid-Market / Enterprise |
| Website in different shapes (`www.`, `https://`, trailing `/`, uppercase) | `accounts.Website` | staging: extract a clean domain |
| Country names inconsistent (`US`, `USA`, `United States`) | `accounts.BillingCountry` | staging: map to ISO country code |
| Amounts sometimes have commas; currency is in a separate column | `opportunities.Amount` | staging: cast to number, convert to USD |
| Two date formats (`2026-03-01` and `03/01/2026`) | `opportunities.CloseDate` | staging |
| Booleans as `true` / `TRUE` / `1` / blank | `contacts.Is_Billing_Contact__c` | staging |

## Billing API (`raw/billing/`)
| Issue | Where | Handled in |
|---|---|---|
| Own customer ID (`cus_...`); CRM ID in metadata for only ~70% of customers | `customers.metadata.crm_account_id` | intermediate: match on CRM ID first, then email domain |
| Some billing emails are personal (gmail/outlook), so domain matching fails | `customers.email` | intermediate: flag as unmatched |
| 2 self-serve customers that don't exist in the CRM | `customers` | intermediate: unmatched table |
| Amounts in cents; mixed currencies (USD, EUR, GBP) | `subscriptions`, `invoices` | staging: divide by 100, convert with an FX seed |
| Unix timestamps in UTC | all billing resources | staging: convert to dates |
| Plan renamed mid-year: `Team` became `Pro` on 2026-07-01 | `invoices.lines.description` vs `subscriptions` nickname | staging: map both to one plan name |
| Annual plans billed once a year | `subscriptions.items.price.recurring.interval` | marts: MRR = annual price / 12 |
| Nested JSON | all billing resources | staging: unnest |

## Product usage files (`raw/usage/`)
| Issue | Where | Handled in |
|---|---|---|
| Column names changed in May (`Domain` became `customer_domain`, etc.) and `api_calls` was added | Jan-Apr vs May-Oct files | staging: column positions line up, so one table reads both; `api_calls` is null before May |
| Two date formats (`01/2026` vs `2026-05-01`) | month column | staging |
| March and August were exported as Excel | `.xlsx` files | load script converts to CSV |
| July was sent twice (`usage_2026_07 (1).csv`) | usage folder | staging: dedupe using the source file name (`"$path"` in Athena) |
| Domains in mixed case, with `www.` and leading spaces | domain column | staging: trim, lowercase, strip `www.` |
| Trial workspaces not tied to any account | domain column | intermediate: unmatched table |

## Answer key
`data/answer_key/account_truth.csv` holds the true mapping and each account's story (healthy, underused, churning, prospect). It is **not** loaded to S3. Use it to check that your mapping models get the right answer.
